**发现并修复日志格式缺陷**：`=== 常驻` 行原来是 `log('\n=== 常驻 ...')`，
开头的 `\n` 让实际输出变成「空行 + 无时间戳的常驻行」：

```
[04:36:38] 
=== 常驻 锦一电台(354892492946)（在线5580 VIP ...）900秒 ===
```

**后果**：任何按 `^\[HH:` 过滤日志的脚本（包括我自己的统计、可能的日报看板）
都会**静默漏掉所有常驻记录**。我第一次统计 4 点档时得出「锦一电台常驻 0 次」的错误结论，
实际是 2 次 × 900 秒。

**修复**：

```js
log('');
log(`=== 常驻 ${disp(g.room)}（在线${g.online}...）${perMs/1000}秒 ===`);
```

**验证（05:01:26）**：

```
[05:01:26] === 常驻 锦一电台(354892492946)（在线5645 VIP 🏆高频发袋(5点历史8次)）900秒 ===
```

**教训**：日志格式是给机器读的契约。「用 `\n` 做视觉分隔」是把展示需求混进了数据结构，

## 2026-11-03 08:58：fudai.sh start 误报「启动失败」（可观测性 bug）

**现象**：执行 `./fudai.sh start` 返回 `❌ 启动失败`，但检查发现进程和 Chrome 全部正常运行。

**根因**：

```bash
nohup bash scripts/run-h35.sh ... &
sleep 6
if running; then echo "✅ 已启动"; else echo "❌ 启动失败"; fi
```

`running()` 只检查 node 进程是否存在。但 supervisor 启动时会**先清理 Chrome 缓存**
（本次清理了 615MB），再拉起 Chrome，最后才启动 node：

```
[08:58:30] [supervisor] 清理 Chrome 缓存 Default/Cache 615MB
[08:58:32] === hunter35 常驻高人气直播间 ===   ← node 这时才启动
```

缓存越大清理越久，实测清 615MB + 拉起 Chrome 共约 **30 秒**，而脚本只等 6 秒 → 必然误报。

**危害**：运维看到「启动失败」可能重复执行 start（虽然有 `if running` 保护不会双开），
但更常见的是误判系统已挂、去排查不存在的问题。

**修复**：改为最多 40 秒的轮询（每 2 秒查一次）：

```bash
for _i in $(seq 1 20); do
  sleep 2
  if running; then echo "✅ 已启动（约 $((_i*2)) 秒就绪）"; return; fi
done
echo "❌ 启动失败，查看 $BASE/h35-supervisor.log"
```

**教训**：启动检查的等待时间必须覆盖「最慢路径」——这里最慢路径不是 node 启动，
而是它前面的缓存清理。**凡是固定 sleep 后做健康检查的地方，都要问一句「最慢情况要多久」**。

### 登录时踩的两个坑

**坑 1：会话级 Cookie 关闭即丢。** 第一次重登，脚本报「账号添加成功」，但 Cookies 库里
只有 `ttwid`，`sessionid` 消失。原因：`sessionid` 是会话级 Cookie（`expires=0`），
Chrome 退出就丢弃。修复：关闭前用 CDP `Network.setCookie` 把会话 Cookie 重设为 30 天持久化，

**坑 2：登录到 accounts/main，启动却还用旧 profile。** `fudai.sh start` 不传账号，

`accounts/main` 存在就带上账号参数。

这样不用 account 模式——**日志、结果、看板路径全部保持在原位**。

### 坑 3：account 模式的日志路径不同

`hunter35.mjs` 在 `--account` 模式下设 `W = accounts/<name>/work`，所以 `h35.log`、
`h35-results.jsonl`、所有状态文件都写到那里，而**看板和巡检还在读 `douyin-auto/`**，
造成「日志 10 分钟不更新」的假死判断。这也印证了「把登录态复制到主 profile」是更省事的选择。

### 坑 4：proc_pids 排除 account 进程导致双实例


`fudai.sh stop` 后 72217（`--account main`）仍在跑，与新启动的进程抢 9750。已去掉该过滤。

### 教训

**「看不见」和「没有」表现完全一样。** 整夜 0 福袋时，我花了几小时分析锦一电台的发袋规律、

### 缺陷 1：`run-h35.sh` 的 profile 路径在账号模式下是错的

```bash
PROFILE="$BASE/chrome-profile"   # BASE=accounts/<名字>/work
```
账号模式下 `hunter35.mjs` 用的是 `accounts/<名字>/profile`，而 supervisor 一直在清理
`accounts/<名字>/work/chrome-profile` —— 一个根本不存在的目录。
**后果**：账号实例的 Chrome 缓存永不回收，长期跑会无限增长。
修法是按有无账号参数分叉，端口也改为「显式传入 > `meta.json` 登记 > 9750」，
并把 `chrome_running()` 里的端口从写死 9750 改为变量（否则实例 B 永远看到「Chrome 在跑」）。

### 缺陷 2：12 个看板守护孤儿造成无限重启风暴（load 冲到 58）

**症状**：系统负载从整夜的 3-4 突然冲到 **58**（8 核机器），CPU 却还有 76% idle。

**根因**：`./fudai.sh web` 每次调用都 `nohup bash web/run-web.sh` 新起一个守护，
**旧的不清理**。实测积压了 **12 个** `run-web.sh`，它们各自 while-true 拉起 `server.mjs`：
抢到 8899 端口的那个在服务，抢不到的立即退出，10 秒后再抢 —— **无限重启风暴**。
代价是 fseventsd 吃掉 50% CPU（进程创建/销毁产生海量文件系统事件），
真正在提供服务的只有一个 server。

**修复**：
1. `run-web.sh` 加 `mkdir` 原子锁，第二个实例直接退出
2. 循环内先判断端口是否已被监听，被占用就只 sleep、不启动
3. 清理掉 12 个孤儿，只留一个守护

**教训**：「进程退出后自动重启」这个模式在**没有单实例保护**时是有毒的。
凡是 while-true 守护，第一件事就该是「怎么保证只有一个我在跑」。

### 缺陷 3：`ps` 把中文路径转义，所有按路径匹配进程的代码静默失效

**这是本次最有价值的发现。** 项目路径含中文（`邓林work/个人项目/抖音福袋`），
而 macOS 的 `ps` 会把非 ASCII 字节转义成 `M-iM^BM^S` 这种形式：

```
$ ps -eo args | grep run-h35.sh
bash <项目根>/scripts/run-h35.sh ...
```

**后果**：所有 `grep -F "<含中文的完整路径>"` 都**必然 0 匹配**，而且不报错。

实测踩到两处：

| 位置 | 表现 | 修法 |
|:---|:---|:---|
| `fudai.sh stop-acc` | 报「已停止」但进程 20 秒后又被 supervisor 拉起 | 只 grep ASCII 片段 `run-h35.sh` + `accounts/<名字>/work` |
| `account-manager.mjs profileInUse` | 防双开保护**永远返回 false** | 改为按调试端口是否监听判断（端口是纯 ASCII） |

**通用规则**：在含非 ASCII 的路径下，**永远不要用 `ps | grep 完整路径`**。
要么只匹配 ASCII 片段，要么改用端口、锁文件、`/proc` 之类与路径编码无关的手段。

## 2026-11-03 11:17：巡检确认「福袋识别但未参与」是规则而非 bug

巡检看到房间 `633986383480` 的福袋从 80 秒倒计时走到 0，日志只有 `[f值检查]`、
没有 `★★ 福袋!` 和参与动作，一度怀疑是缺陷。查代码后确认**这是设计好的规则**：

```js
var secLeft=(typeof d.fudai.sec==='number')?d.fudai.sec:-1;
if(secLeft>=0 && secLeft<180){ await sleep(2000); continue; }   // 剩余不足 180 秒直接跳过
```

原因是实测剩余不足 3 分钟的福袋**点不开面板**，参与必然失败。

**但这个规则反过来暴露了真正的浪费**：系统 11:15:16 才换房进来，福袋已经只剩 80 秒。
它不是「抢不到」，是「来晚了」——福袋在 11:13 就已经开始，而那段时间系统正在
11:03 那次参与的守候循环里（见上一节）。

**两件事叠加的完整链条**：
1. 11:03 参与成功 → 守候 730 秒，期间系统完全停摆
2. 11:13 同房间开新福袋 → 守候循环只扫中奖弹窗，不扫福袋图标 → 错过
3. 11:15 守候结束换房到另一个房间 → 该房间福袋只剩 80 秒 → 按规则跳过

所以「守候期间停摆」和「换房时机错位」是同一个问题的两端，不能分开处理。

**顺带观察**：今天连续两个「三角洲行动」类游戏直播间发福袋（`564078693536` 新光、
`633986383480` 海超人），且福袋间隔约 10 分钟。游戏类房间的福袋密度明显高于其他品类，
与评分里 `GAME_STRONG_PAT` +15 的方向一致，但这个方向可以再加强。

## 2026-11-03 14:00：三处自检误报与「日志跨天」统计陷阱

### 自检脚本连续两次误报，都出在「页面长度」这一个指标上

`check-alive.sh` 用页面 `len` 判断登录态，但抓取每次换房都会导航，撞上不同加载阶段会读到完全不同的长度：

| 时刻 | 读到 len | 脚本判定 | 实际 | 根因 |
|:---|:---|:---|:---|:---|
| 12:57 | 14 | `OK len=14`（自相矛盾） | 正常 | len<60 时才重测，但输出里仍带着 14 |
| 13:57 | 342 | `SUSPECT_SHORT_PAGE` | 正常 | 修重测时阈值写成 `len>=60` 就 break，342 直接跳过重测 |

**正确判据不是「长度多少」，而是「长度是否已经稳定」**：

```js
let len=0, prev=-1, stable=false;
for(let a=0;a<8;a++){
  const d=await send('Runtime.evaluate',{expression:'(document.body.innerText||"").length',returnByValue:true});
  len=d.result.value||0;
  if(len>=350 && Math.abs(len-prev)<40){ stable=true; break; }   // 连续两次相近且够长
  prev=len;
  await nap(1800);
}
```

**教训**：「单次采样 + 阈值判断」在页面会连续导航的场景里必然误报。
要么连续采样到稳定，要么用与加载状态无关的判据（Cookie 就是这样的硬证据）。
**更严重的代价不是白排查一轮，而是误报多了之后真告警会被忽略。**

### 日志 `h35.log` 跨天，任何按日志数数的统计都会错

`h35.log` 是 append 模式，只受「超 20MB 截到 5000 行」限制，**不按天切**。
当前这个文件从 **11-02 11:38** 一直写到 11-03，跨了两天。

而日志每行只有 `[HH:MM:SS]`，没有日期，于是：

```
$ grep "参与成功" douyin-auto/h35.log
24:[11:39:20] ✅✅ 参与成功(maybe-joined)   ← 这是 11-02 的
10383:[10:20:43] ✅✅ 参与成功(joined)      ← 这才是 11-03 的
```

**我因此把「今日参与 3 次」报给了用户，实际只有 2 次。** 对照 `h35-results.jsonl`
里同一条记录写得很清楚：`"at": "2026-11-02T03:39:20.081Z"`（UTC，对应北京 11:39:20）。

**固化的统计规范**：

- **今日/区间战果一律以 `data/participations.jsonl` 为准**（带完整 ISO 时间戳，可精确按日过滤）
- **`h35.log` 只用来看实时状态与排查过程**，不要用它数次数、算成功率
- 看板 `dedupRows` 读的就是 jsonl，所以看板数字是对的；错的只有我用 grep 数出来的

如果要彻底解决，可以让 `log()` 输出 `[MM-DD HH:MM:SS]`，但那会破坏所有依赖
`^\[HH:MM:SS\]` 的解析（看板、日报、巡检脚本十几处），收益不抵风险，暂不动。

## 2026-11-03 15:00：下午出现「多房间同时加载失败」，与历史「单标签卡死」不是同一回事

**现象**：14:00-14:39 的 40 分钟内，连续 5 次 `页面空白(len=20)，重建标签后重试`，
但每一次后面都跟着 `重建后仍失败(len=20)，换下一个候选`。

**关键区别：这 5 次是 5 个不同的房间，不是同一个坏房间。**

| 时刻 | 房间 | 在线 |
|:---|:---|:---|
| 14:00:19 | 莎莉马佳佳 39619203233 | 10000 |
| 14:02:55 | 乱斗教授 544590831076 | 20000 |
| 14:03:26 | 智勋（三角洲行动）712289279749 | 10000 |
| 14:36:43 | 华少减重版 104090142313 | 10000 |

而文档里记录的「标签级卡死」是：**同一个标签**坏掉后加载任何房间都是 len=20，
但**新标签**访问同一房间完全正常。两者表现相似、根因完全不同：

| 判据 | 单标签卡死（已修） | 本次多房间失败 |
|:---|:---|:---|
| 影响范围 | 所有房间都打不开 | 只有被选中那几个房间 |
| 重建标签后 | **恢复正常** | **仍然失败** |
| 恢复方式 | 重建标签 | 换候选房间 |
| 之后的状态 | 持续可用 | 14:39 后自行恢复 |

**所以这次不是标签问题，更像服务端不给内容或请求被限流。** 当时系统负载 8-11
（8 核），内存也在换页，可能有关，但没有证据。

**判断标准**（下次遇到按此判断，不要误用「重建标签」的结论）：

1. **重建标签后能恢复** → 是老问题（标签级卡死），自愈逻辑已经覆盖，不用管
2. **重建标签后仍失败，但换房间正常** → 本次这类，属于单房间加载问题，换候选即可
3. **重建标签后仍失败，且换房间也失败** → 才是真故障（网络/登录态/限流）

**当前处理**：不处理，继续观察。20 分钟 5 次的频率还不足以定性，
但如果升到「每小时几十次」或「换房间也失败」，就要查网络与限流。
